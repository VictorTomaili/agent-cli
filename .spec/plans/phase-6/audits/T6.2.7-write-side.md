## Findings

### F1 - Host-supplied `cwd` argument is honored, bypassing the LAUNCH_CWD trust boundary (A17)

Severity: **Medium** (escalates to **High** when the server process runs with elevated
privileges, e.g. as root in a container or a host-level daemon; in the common local
stdio deployment the impact is bounded to directories the user may already write).

File: `src/api/write.js:73` (`const LAUNCH_CWD = process.cwd();`) and the
destructured defaults `cwd = LAUNCH_CWD` at `src/api/write.js:111-117`
(`brainWrite`), `:190-193` (`lessonCapture`), `:543-548` (`memoryUpgradeApply`),
`:616-620` (`lessonConsolidate`); the value is consulted for path resolution at
`src/api/write.js:148` (`identityFilePath(kind.toLowerCase(), scope, cwd)`),
`src/lessons-lib.js:367` (`lessonsRoot(scope,cwd)/.inbox`), `src/memory-upgrade.js:250/295`
(`identityBase(scope,cwd)`), `src/consolidate.js:375-376` (`lessonsRoot/coreFile(scope,cwd)`).
Reachable via `src/serve.js:548`:
```js
const result = await writeTool.call((params && params.arguments) || {});
```
The MCP `inputSchema` for these tools (serve.js:100-238) does NOT declare a `cwd` key,
but `tools/call` passes the raw `params.arguments` object through unvalidated, so a
host can inject `cwd` even though it is not advertised.

Repro (verified on disk via `handleMessage`, isolated `AGENT_CLI_HOME`):
```
initialize: { capabilities: { experimental: { agentCli: { writeTools: true } } } }
tools/call: {
  name: "brain_write",
  arguments: { kind: "SOUL", scope: "project", content: "PWNED", applyChanges: true,
               cwd: "/tmp/t627-escape2-988950" }   // attacker-chosen absolute path
}
```
Observed:
```
mcpResult_ok:  true
fileExists:    true
fileContent:   "PWNED"
absolutePath:  "/tmp/t627-escape2-988950/.agents/SOUL.md"
```
`/tmp/t627-escape2-988950` is outside the probe `AGENT_CLI_HOME` AND outside
`LAUNCH_CWD` (`/tmp`, the module-load `process.cwd()`). The same argument was used
to write the project inbox to the attacker path via `lesson_capture`
(`<cwd>/.agents/lessons/.inbox/demo.md`) and to make `memory_upgrade_prepare` read
`<cwd>/.agents/.schema-version`. The dry-run for `cwd:"/etc"` echoed the resolved
destination `/etc/.agents/SOUL.md`.

Impact: The `cwd` parameter is documented (write.js:69-73) as honored-only-at-launch,
"callers cannot smuggle in a project root via the `cwd` argument". That is false. A
host is able to select the *destination project root* (and therefore the write target
directory) for project-scoped writes from an MCP argument, writing arbitrary content
to `<chosen-dir>/.agents/<file>` for SOUL / LESSONS / ENVIRONMENTS (brain_write),
writing inbox captures anywhere (`lesson_capture`), and operating on / pruning lessons
under any directory (`lesson_consolidate`). This is a direct violation of the A17 trust
boundary ("no MCP argument selects a project root / destination path; cwd is always
the server launch dir (LAUNCH_CWD), never host-supplied"). The write is bounded to a
`.agents/<identity-file>` suffix under the chosen cwd (or `.agents/lessons` /
`.agents/<kind>.md` for the lesson functions), so it is not a fully arbitrary-path
write, but it is arbitrary-content write to a host-selected location — a real path-
selection primitive the design explicitly forbids.

Note: the same finding surfaces as a mild A15-adjacent leak — the dry-run `data.path`
echoes the resolved destination (e.g. `/tmp/tmp.<home>/.agents/SOUL.md`), disclosing the
write target to the host. That value is derived from the host's own `cwd`/scope args, so
it is not a new disclosure; it is called out only as corroborating evidence that the
host controls the destination.

Recommended fix: ignore a host-supplied `cwd` for path resolution entirely. Because
`cwd = LAUNCH_CWD` is a *default*, any caller-supplied value overrides it. Replace the
destructured-default pattern with a hard clamp at the top of each public function:
```js
const resolvedCwd = LAUNCH_CWD;            // always the module-load cwd — never the arg
// use `resolvedCwd` for every identityBase/lessonsRoot/coreFile/identityFilePath(...) call.
```
i.e. either drop the `cwd` parameter from the MCP-reachable write SDK functions, or keep
it only for the low-risk diagnostic echo and pass `LAUNCH_CWD` (not the captured arg) to
`identityFilePath`/`lessonsRoot`/`coreFile`/`identityBase`/`atomicEnableProjectTarget`.
Add a regression test asserting `brainWrite({..., cwd:"/etc"})` and a
`tools/call brain_write` carrying a `cwd` still resolve the destination under
`LAUNCH_CWD` (and, for the dry-run, that the echoed `data.path` is under LAUNCH_CWD).
Also update the misleading comment at write.js:69-73.
